# Local Service Insight extensions

Install netKonnect 1.8.0, then use **Preferences → Destination identification** to enable each browser you want to observe and save its extension. Firefox, Chrome, Edge and Enhanced Lookup have independent switches, all off by default. The extension also has a Pause button. Disabling a bridge stops accepting that browser's observations and clears its recent evidence; previously measured SQLite history remains.

For Chrome or Edge, extract the saved ZIP to a permanent local folder. Open `chrome://extensions` or `edge://extensions`, turn on Developer mode, choose **Load unpacked**, and select that folder. The manifest contains a public key to keep a stable extension ID; each browser has its own ID and native host allowlist. These development extensions persist across browser restarts. They are not store-published packages. A future store release must use its actual catalog ID in the host allowlist.

For Firefox 140+, load the saved unsigned XPI through **about:debugging → This Firefox → Load Temporary Add-on**. Temporary loading ends when Firefox closes; persistent customer distribution requires Mozilla signing.

Reload an ordinary streaming tab after connecting the extension. Already-started requests may not generate new response events. Check Preferences for the matching browser's **connected** status and recent request observations. Each browser profile must load the extension if it should contribute evidence. Browser APIs do not provide a profile/process/socket identifier that can distinguish multiple profiles of the same browser at a shared endpoint.

All three integrations send request hostnames, server IPs and destination ports, page hostname context, request kinds, phases and recent timestamps through local native messaging and authenticated Windows IPC. Private windows and cache-only responses are excluded. Full URLs, paths, queries, headers, cookies, titles, page bodies, raw certificates and browsing history are not sent or read. No content scripts, debugger access, browser DNS queries or external requests are used. An extension's own installation requires its browser permissions; enabling the app switch alone does not install it.

Firefox additionally reports available TLS, certificate issuer/subject, secure DNS and Encrypted Client Hello metadata. Chrome and Edge's standard passive request API does not expose those fields. A Chromium response status line may be synthesized, so it is shown separately from negotiated HTTP version. Chromium extensions read proxy configuration mode; they never change it or send proxy addresses, PAC URLs or credentials. Direct-mode requests can correlate with sockets; system-mode requests require known, unconfigured Windows system proxy settings. Fixed proxy, PAC, auto-detect and uncertain modes remain visible in recent observations but are excluded from socket naming. Conservative exclusions can leave a service unidentified even when an auto-detect configuration ends up choosing direct access.

Requests match recent endpoints by browser family, normalized server IP and destination port. Chromium observations cannot label Firefox, and Edge observations cannot label embedded Edge WebViews. These are timed destination clues, not per-tab byte counts or proof that every byte at a shared endpoint belongs to the named service. Active observations refresh every 15 seconds and expire after 45 seconds; completed/error observations expire after 15 seconds. A native connection keeps a Chromium service worker awake; an alarm retries when it becomes unavailable. After worker suspension or bridge loss, metadata for requests that began earlier may be unavailable until new requests start.
